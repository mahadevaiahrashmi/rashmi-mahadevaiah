# Inversion

## What It Is
Inversion, championed by Charlie Munger (Berkshire Hathaway), is a mental model that approaches problems backwards: instead of asking "How do I succeed?", ask "What would guarantee failure?" By identifying what would make something fail, you can avoid those pitfalls. It complements forward thinking and often reveals risks that positive planning misses.

## When to Use
- Strategic planning — stress-testing a strategy by imagining its failure
- Risk identification before launching a product or initiative
- When forward thinking isn't producing useful insights
- Decision-making when you're stuck between options — invert to see which risks are worse

## When NOT to Use
- When you need specific action plans — inversion identifies what to avoid, not what to do
- As the only thinking tool — pair with forward-looking frameworks
- When the team is already pessimistic — inversion can amplify negativity if used in isolation

## How to Apply
1. **Define the goal**: What are you trying to achieve?
2. **Invert**: Ask "What would guarantee this fails?" or "What is the opposite of what I want?"
3. **List failure modes**: Brainstorm every way this could go wrong. Be specific
4. **Prioritize**: Which failure modes are most likely and most damaging?
5. **Prevent**: For each critical failure mode, define how to avoid it
6. **Synthesize**: Your strategy = forward plan + inversion-derived guardrails

## Example
**Goal**: Launch a successful developer platform
**Inversion**: "How would we guarantee developers hate our platform?"
- Bad documentation with no examples → Prevention: Docs-first development, runnable examples
- Breaking API changes without warning → Prevention: Versioning policy, deprecation notices, migration guides
- Slow, unreliable API with no status page → Prevention: SLA commitments, public status page, latency monitoring
- No community or support → Prevention: Discord community, responsive forum, office hours
- Pricing that punishes growth → Prevention: Generous free tier, predictable pricing, spend alerts

**Key Insight**: The fastest way to fail is bad documentation + breaking changes. These are table stakes, not differentiators.

## Key Pitfalls
- Being too vague ("it could fail if people don't like it") — be specific about failure mechanisms
- Using inversion to justify inaction — the point is to prevent failure, not to avoid trying
- Only doing inversion without forward planning — you need both perspectives
- Ignoring low-probability, high-impact failures — those are often the most dangerous

## Related Frameworks
- **Pre-mortem** — Gary Klein's structured version of inversion applied to specific projects
- **First Principles** — complementary forward-thinking approach
- **Second-Order Thinking** — considers downstream consequences that inversion may reveal
- **Root Cause Analysis** — inversion applied to existing problems
